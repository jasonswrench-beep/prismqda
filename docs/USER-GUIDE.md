# PrismQDA user guide

PrismQDA is a free program for analysing qualitative data: interviews, open-ended survey answers, documents, pictures, recordings (with or without captions). You read your material, give passages and areas **codes**, write **memos**, ask questions of your coding, and take the results out as Word and Excel files. It runs on your own computer and keeps everything there.

This guide follows the program as it is today. Where something is not built yet, it says so, and the list of what is missing is at the end.

## Before you start

- **A project is one file** ending in `.pqda`. Your documents, pictures, codes, codings, memos, and the log of what you did are all inside it. Copy the file to move or share the work. Nothing is kept anywhere else.
- **Every change is saved as you make it.** The status line at the bottom says "Saved". There is no Save to remember, and you can undo with Ctrl+Z.
- **Nothing leaves your computer on its own.** The program connects to nothing by itself. The one exception is the **Check for updates** button in Settings, which you press. The AI Assistant builds text that *you* paste into a chatbot if you choose to (see below).
- **The window has a ribbon** along the top (Home, Import, Code, Memos, Explore, and so on). The ribbon only changes which commands are on show; the work happens in the pages below it. A bar at the top of a page leads back to the coding workspace.
- **A portable copy.** The release has a zip, `PrismQDA_<version>_portable.zip`, that you unzip anywhere (a folder, a USB stick) and run without installing. It keeps its settings, its list of recent projects, and any translations you added in a folder called `PrismQDAData` beside the program, so you can carry the whole thing. Your projects are still the `.pqda` files you save wherever you choose. Delete `portable.txt` from beside the program to make it use your Windows profile again.
- **A first look.** From the start screen you can open **Practice on a sample project**: a small made-up study with documents, codes, and coding already in it, to try everything on before you use your own data.

## Starting and opening a project

- **New Project** asks for a name, where to save the file, and, if you like, your research question, a method template, and whether you will code **any stretch of words** or **whole units** (a paragraph, an answer, a turn). Choose whole units if your method needs every coder to code the same pieces, as in content analysis.
- **Open Project** opens a `.pqda` file. If it was made by an older version, it is brought up to date and an untouched copy of the old file is kept beside it.
- **Double-click a project.** The installer makes `.pqda` files open with PrismQDA, so a project can be opened from Windows Explorer. If PrismQDA is already open, the file opens in that window and the project that was open is closed, as when you choose another from the recent list (PrismQDA does not start a second window). A project that is already open is left as it is, a file that cannot be opened is said in the bar at the bottom, and an encrypted project asks for its passphrase. The portable copy does not set this up, since it changes nothing in Windows; it is a window of its own and can run beside an installed copy.
- The start screen lists **recent projects**. A project that was moved says "not found" and offers to **Locate** it.
- **Backups.** A dated backup copy is made every time a project opens, and you can make one at any time from the Code tab (Backup). Settings lets you choose a folder for backups and how many to keep.

## Getting your material in

Open **Import Data** (the Import tab, or Add Documents). Choose files, check what each will become, and import.

| What you have | What it becomes |
| --- | --- |
| Text, Markdown, HTML, Word (`.docx`), OpenDocument text, RTF, PDF | A document. Headings and paragraphs become units. |
| A spreadsheet or SPSS file (`.xlsx`, `.csv`, `.sav`) | One case per row, with the text columns as documents and the other columns as **variables** of the case. You say which column is which before importing. |
| A PrismStatistics project (`.pstat`), such as an evaluation or a course survey kept there | The same as a spreadsheet: one case per row, the open comments as documents to code, and the other variables (ratings, groups, hours) as **variables** of the case, with their value labels and missing codes. Only the data is read. See *Coding the open comments of an evaluation*. |
| Interview transcripts and caption files (`.vtt`, `.srt`) | A document with one unit per turn; speakers are kept. |
| A recording with its captions beside it | The transcript, linked to the recording, so the text follows the sound and you can code while it plays. |
| A recording with no captions | A document of its own, with a description for you to write. You code it by stretches of time. |
| A picture (PNG, JPEG, GIF, WebP, BMP) | A document whose text is a **description** you write (what a screen reader speaks). You code **areas** of the picture. |
| A reference library (RIS, BibTeX, CSL JSON), e-mail (`.eml`, `.mbox`), saved web pages, news feeds | One document per item, with the details (author, date, subject) kept as variables. |
| An exchange file from Prism Reference Manager (`.json`) | One document for each **source**, holding its details, its abstract, and its **excerpts** (the words taken from it, the kind of excerpt, the page, and your own note), each excerpt a paragraph; one case for each source. See *Coding a literature review from the library*. |
| A whole folder | Every readable file in it, one at a time. A file that cannot be read is reported and the rest still go in. |

**Coding the open comments of an evaluation.** An evaluation or a course survey kept in PrismStatistics is a `.pstat` file, and Import Data opens it like a spreadsheet. The window guesses which variable names the respondent (one called *id*, *participant*, or *respondent*, with no value twice) and which hold the comments (answers of several words); you can change both, and say how each other variable comes in. Ratings come in as variables of the cases with the labels the file gave their values ("1 Poor" ... "5 Excellent") and the codes it marks as no answer, so the cases can be compared by rating in Explore and in the joint displays of Mixed Methods. Code the comments as you would any answers, and **Export > The case table for PrismStatistics** sends the cases back with their ratings and a variable for every code, the respondent's id as each case's name, so that PrismStatistics can match the table to its own data. The file's own analyses and results are left behind (the import report says so), and the file is never changed. PrismQDA does not keep a variable's long label (the *Overall rating* of a variable called `rating`); the variable comes back under its name.

**Coding a literature review from the library.** In Prism Reference Manager, export a project's notes as an exchange file, and bring it in here (Import Data > Reference library, or any file picker: PrismQDA tells the file by what is inside it). Each source becomes a document with its details and abstract and then its excerpts under *Excerpts*, one paragraph each: *Quotation, page 12*, the quoted words, and *Note:* with your own. An excerpt that came from an AI tool, whose place in the source was not confirmed, or whose quoted words were edited after they were taken says so on its first line. An excerpt taken from two sources is written once, in the first, with the other named; an excerpt with no source in the file goes into one document of its own. Each source is also a case, with its authors, year, where it appeared, its citation key, and its id in the library as variables, so a review can be coded and then compared by year or kind of work. Nothing is sent back to the library: PrismQDA keeps each source's id and each excerpt's id and place in the document's settings, so that a later version can name them.

Things to know:

- **Duplicates.** A file you already imported is said to be a duplicate, and you decide whether to import it again.
- **Destination folder and case.** You can file new documents in a folder and give them a case as they come in.
- **Replacing a document's text.** If a document is revised outside the program, import the new version as its replacement: the text changes and every coding follows the words that survive. A backup is saved first, because this cannot be undone with Undo.
- **Photographs.** If a photograph carries the facts its camera wrote into it (when, with what, and where), Import Data tells you and offers to keep any of them as variables of a case named for the picture. Nothing is kept unless you tick it, and the place has its own tick with a warning, because a precise place can show where a person lives.
- Only PNG, JPEG, GIF, WebP, and BMP pictures are kept. Save anything else as one of those first.

## Coding

Coding is giving a code to a passage (or to an area of a picture). Several coders can code the same material; each coding remembers who made it.

### The coding workspace

The coding workspace has four areas, and F6 moves between them:

- **Documents**: your documents, in folders.
- **The reader**: the open document, with coded passages marked in their codes' colours and the coders' stripes down the side. A second document can be opened beside it (Split view).
- **Codes**: the codebook as a tree, with how often each code is used.
- **Segment Details**: the coding you have selected: its words, its code, who coded it, when, a note, a rating, and its history.

Below the reader, **Retrieved Segments** lists the passages coded with the codes you choose (see "Finding and listing passages").

### Coding words

1. Select words with the mouse, or with Shift and the arrow keys.
2. A small bar of your favourite codes appears above the selection; press one, or press **Enter** to type part of a code's name and pick it from a list.
3. Or press a number **1 to 9** to apply the favourite code with that number.

Other quick keys, which work while the text has the focus:

| Key | What it does |
| --- | --- |
| I | **In vivo**: make a code named from the selected words and apply it |
| R | Repeat the last code you applied |
| U | Select the whole unit at the caret |
| N and Shift+N | Go to the next or previous unit with no coding |
| E | Open the coding at the caret in Segment Details to edit it |

In a project that codes **whole units**, a number key with nothing selected codes the unit at the caret.

To change or remove a coding, select it and use **Options for this coding** in Segment Details: change its code, add a note ("why did you code it this way?"), rate it from 1 to 5 (for codes that are rated), mark it as an example for its code, or remove it. Ctrl+Z undoes any of these.

### Coding pictures

Open a picture and draw an **area**: a rectangle, an ellipse, or an outline made of corners (with the pointer, or entirely with the keys: press O for an ellipse, Space to start, the arrow keys to move and Alt with an arrow to resize, Enter to finish). Then give the area a code the same way as for words. Areas are listed under the picture, shown in Segment Details with a small picture of the area, and counted beside words everywhere (Retrieved Segments, Explore, exports). Write the picture's description first or last; it is the text a screen reader speaks.

### Coding the pages of a PDF

A PDF you import keeps its file inside the project, beside the words that were read from it. The header of the document has two buttons, **Words** and **Pages**. Words is the document as it always was. **Pages** shows the PDF one page at a time, drawn as a reader would draw it, so you can code what words cannot reach: a figure, a table, a scanned stretch, a signature. Draw a **rectangle** on the page (with the pointer, or with the keys: press B, Space to start, the arrow keys to move and Alt with an arrow to resize, Enter to choose a code), then give it a code the same way as for words. An area is always a rectangle; it belongs to the page it was drawn on.

Turn pages with the arrows or the page box in the toolbar, Page Up and Page Down, or Home and End. A page first fits the width of the window and scrolls; **Whole page** fits all of it. Under the page are the coded areas of that page, the pages that have areas (press one to go there), and **The words read from this page**, which is also what a screen reader is told about the page. Areas appear in Segment Details and Retrieved Segments with a small picture cut from the page and their page in words, count beside words everywhere (Explore, exports, a merge), and Word and Excel exports show each one cropped out of its page.

A PDF imported before this was built, or one whose pages could not be drawn, has only its words. The document says so and asks you to choose the PDF again to keep it with the document; its words and their codings stay as they are.

### Coding with a recording

A recording with captions opens with a player above the transcript. The text follows the sound as it plays, and the player follows the text when you move through it. Code the transcript as you would any text.

A recording is linked from where it is on your computer, and PrismQDA only opens one from a **drive with a letter**: `C:\Recordings	alk.mp3`, or a network folder that you have given a letter in Windows (`Z:	alk.mp3`). It does not open a recording named by a network address that starts with two slashes (`\server\share	alk.mp3`), and a project or exchange file that names one is told as a recording that is not found. The reason is that merely asking whether such a file exists makes Windows connect to that server and offer your sign-in to it, and a project or exchange file that someone sent you could name any server. To use a recording on a network folder, give the folder a drive letter first and link the recording again.

### Coding a stretch of a recording

PrismQDA does not turn speech into text. A recording with no captions beside it (a WebVTT or SubRip file with the same name) is not refused: it comes in as a **document of its own**. Its text is a short description that you rewrite (who speaks, where and when it was made, what it is about); the recording stays where it is on your computer, and the project keeps only where it is. Open the document and the player has the tools for coding **stretches of time** under it. (On a transcript, the same tools are folded away under *Code a stretch of the recording*.)

1. Move the recording to where a stretch starts. Play it, drag the player's bar, click the timeline, or type a time in *Starts at* (`1:05`, `1:02:03`, or seconds such as `65.5`).
2. Press **Mark start** (or the key **I**). Move to where it ends and press **Mark end** (or **O**). The line under the buttons tells the stretch in words: "Recording, 0:12 to 0:45 (0:33 long)".
3. Give it a code the way you give a code to words: **Apply a code…**, the favorite number keys, or the Codes list. The marks are let go and the stretch is chosen, so a second code goes to it the same way.

Each coded stretch is a stripe on the **timeline** (stretches that overlap are in rows of their own, and the line is the recording's place). Under the timeline is the **list of coded stretches**, each with **Play** (it plays from the start of the stretch and stops at its end), **Start here** and **End here** (they move the start or the end of the stretch to where the recording is now). **Segment Details** tells the chosen stretch and has *Play this stretch*. The recording never starts by itself: it plays only when you press a Play button or the player's own.

**The waveform.** Under the player, *Show the waveform* draws how loud the recording is from its start to its end, with the coded stretches shaded behind it (in the colors of their codes) and the place the recording is now. It is drawn only when you ask, because the whole sound has to be read to draw it; the sound is decoded by the window itself and nothing leaves your computer. Click it, or use the arrow keys (5 seconds, 30 with Shift; Home and End), to move the recording to a place; this does not start it. Under the picture, a line says where the loudest part is, which helps in finding where someone raised their voice or where a recording is silent. A recording larger than 250 MB, or longer than about three hours, is not drawn (the whole sound is held in memory while it is read), and the page says so.

**Saving a stretch as its own sound file.** Under the list of coded stretches, type where to save (a folder ending in a slash, such as `C:\Clips\`, or a full file name) and press **Save sound** on a stretch. The file is a WAV file of just that stretch (16-bit, the channels of the recording; for a video, only its sound; at 44.1 kHz, or at a lower rate for a recording longer than about half an hour, because the whole recording is read into memory to cut it: 22.05 kHz up to an hour, then 16 and 11.025 kHz, and none beyond two hours, which the page says in words), named for the document, the times and the codes when you gave a folder: `Interview 3 1m05s-1m32s Safety.wav`. With the path left empty, Windows' own save window opens. A file that is already there is never replaced from a typed path. If a list of names is being applied to exports, the page says that a sound cannot have names taken out of it: listen to the file before you share it.

A stretch counts everywhere that a coded passage or a coded area counts: the code's count, Retrieved Segments, Explore (two stretches overlap when they share time), the report, and the Word and Excel exports (CSV and Excel add the two times in seconds). Agreement between two coders on a recording is measured in cells one second long. A merge brings a stretch only when its recording is at the same place on this computer.

**Playing the clips of a code one after another.** In Retrieved Segments, when the rows hold coded stretches of recordings, a **Clips** button appears with the filters. Filter to a code (or search for a document), press *Clips*, then **Play all the clips**: each stretch plays from its start to its end and the next one follows, in the order of the table, across recordings. *Previous clip*, *Pause*, *Next clip* and *Stop* act on the one playing, and a line under them says which clip it is ("Clip 2 of 7: Interview 3, 1:05 to 1:32, Safety.") so that a screen reader announces each change. A recording that cannot be found is said and passed over. Nothing plays until you press *Play all the clips*.

## The codebook

Open the **Codebook Editor** from the Codes area or the View tab.

- **Codes** have a name, a colour, a **definition**, and rules for **when to use** and **when not to use** them. A **theme** is a code that groups other codes. Drag a code onto another to make it a sub-code, or use Alt with the arrow keys.
- **Examples.** Mark codings as *anchor examples* of a code, so a new coder can see what it means; mark *counterexamples* for what it does not.
- **Mutually exclusive groups.** Put codes in a group when only one of them may be given to the same words by the same coder (for example, a sentiment). The program says when a coding would break the rule and offers to replace the other.
- **Rated codes** let each coding carry a rating from 1 to 5, described by a label ("Intensity") and what a 1 and a 5 mean.
- **Merge** two codes into one, **split** a code, or **retire** one you no longer use (retired codes cannot be applied but are kept). Merging and splitting are written in the log and are not undone with Undo.
- **Versions.** Save a version of the codebook at a milestone and compare any two versions, or a version with the codebook today.

## Memos and cases

- A **memo** is writing that travels with what it is about: the project, a document, a code, a coding, or an area of a picture. Kinds: analytic, reflexive, method decision, and to do. Memos are on the **Memos** page, in Segment Details, and in the Memos area.
- A **case** is whatever you want to compare across: a participant, an organization, a school. A case holds documents; its **variables** (age group, site, date) come from an imported spreadsheet or from the facts of a photograph, and Explore can group by them.

### Links between passages

A link says how one coded passage relates to another: it *contradicts* it, *explains* it, *leads to* it. Select a coded passage so that Segment Details shows it, press the plus beside **Links**, choose which way the relation runs (this passage does it to the other, or the other does it to this), type the relation (any word or two; the ones you have used and some common ones are offered), find the other passage by typing words of it, its code, or its document, and press **Link them**. The passage then lists the link, and so does the one at the other end, the other way round ("This passage explains", "explains this passage"). Press a linked passage to open it in its document, or the cross to remove the link; **Undo** takes either back. The **Synthesize** page lists every link, and can show only one relation. If you remove a passage its links disappear from the lists, and come back if you undo the removal. When coders' work is merged (and when a packet that carries the codings is made), the links whose two passages are in both projects come along.

## Finding and listing passages

- **Search** (Ctrl+K) finds words in your documents and also finds commands, codes, and documents by name.
- **Retrieved Segments** lists every coding in scope. Choose the **codes**, the **documents**, and the **case** to look at, type in the search box to narrow the list, press a row to jump to its words, and sort by any column. Check rows to act on several. The **Gallery** button shows the areas of pictures as tiles under their codes instead.
- **Export segments** in the same menu takes the passages out as Excel, Word, or CSV (see "Reports and exports").

## Working with a part of the project: the working set

When a study has many documents, cases, and codes, you can choose the ones to work with once and have the pages follow. Open **View > Filters > Working Set** (or Ctrl+K and type *working set*). For each of **Documents**, **Cases**, and **Codes** either leave *Every ...* ticked, or untick it and tick the ones you want (there is a box to find by name; ticking a code ticks its sub-codes, and each can be unticked again). Press **Apply**. A bar under the ribbon then says what is narrowed ("Working with a part of the project: 3 of 12 documents; 1 of 4 cases"), on every page, with **Change** and **Show everything** beside it.

- **What follows it:** Retrieved Segments, Explore (the code summary and profile, the matrix, the relations, queries, cross-tabulations), the Themes page, Text Analytics, Statistics (the cases of every analysis, and so of a page kept in the notebook, which records them), the AI Assistant, and the sample for agreement. Each is asked only about what you chose; where a page already has its own choice (the documents you picked in Text Analytics, say) it uses what is in both. A set of **cases** narrows the pages that read documents (Retrieved Segments, Text Analytics, the AI Assistant, the sample) to the documents those cases hold. Where a page would otherwise read an empty list of codes as every code (Text Analytics words, a prompt packet, Code Relations), a working set that leaves no code to ask about is refused in words and nothing is sent.
- **What does not:** the Data table, the documents list, the Codebook Editor, the Team page (agreement, disagreements, merge, packets), reports, and the exports (the coded passages can be exported from the final layer by ticking it in the export dialog); nor the examples of a code in the detail panel and the passages behind a number in Explore, which always show every passage. The whole project is still there, and still what those use.
- **What is not changed:** a page that shows results made before you changed the set (a query, a word count, a prompt packet) keeps them until you run it again, and says so on the page; a page kept in the Statistics notebook keeps the cases it was run on, and says how many; pages that reload by themselves do so at once.
- Nothing is hidden or removed from the project, and the set is forgotten when you close the project.

## Themes

A theme is a code that groups other codes. The **Themes** page (Code ribbon > Themes, the menu of the Codes pane, or Ctrl+K and type *themes*) is where you group codes into themes, check each against its passages, and define it, which is the third to fifth of the six phases of a reflexive thematic analysis. **Add a theme** asks for a name and, if you like, a sentence of what it says. Each theme is then a card with its **stage** (*Candidate*: a grouping that might hang together; *Reviewed*: checked against its passages and against the data as a whole; *Defined*: named and defined, ready to be written up), its name and definition (change them there and press *Save name and definition*), how many passages, documents, and cases it holds, the **codes under it** each with its passages and documents, and up to three **quotations** that show it: the passages you marked as examples of its codes first, then the first passages of them. Press *Passages* beside a code to list its passages, and *Open* beside a quotation to open it in its document.

To put a code under a theme, **drag it onto the card** with the mouse (drop it on *Codes under no theme* to take it out; Escape stops a drag), or choose the theme in the list beside the code (the list is the way with the keyboard and a screen reader). Under the themes are the **codes under no theme**: the ones still to place. Tick several and press *Make a theme from the ticked codes* to make them a theme together. The codebook shows the same grouping, because a theme's codes are its sub-codes there; to take a code out of a theme choose *Under no theme*. **Make a thematic map** draws every theme and the codes under it as a concept map (named *Thematic map*) and opens it in Explore, where you can move the boxes about and add to it. **Ask an AI for candidate themes** (at the foot of the page) works like the AI Assistant: PrismQDA calls no AI. *Build a packet for a chatbot* makes text from the **names, definitions, and number of uses of your codes, and no passage of any document**, which you copy into a model of your choice; then name the model, paste its answer, and *Check the answer*. The checker drops a code the packet did not name, keeps a code that was placed twice in the first theme only, and refuses a theme left with fewer than two codes, and tells you each time. What passes waits: press *Accept as a candidate theme* (you may rename it first) to make the theme, move its codes under it, and add a memo that says where it came from, or *Reject*. The packet cannot be built while the offline lock is on, or while AI is off in Settings, and a code marked do not share is left out. The AI log keeps the packet, the answer, and your decisions.

The report's **Themes** section (Report > Build a report) puts each theme, its stage, definition, codes, counts, and quotations into the Word file, and names the codes that are under no theme.

## Explore: asking questions of your coding

The **Explore** page holds the tools for questions. Each result is a table you can read with a screen reader and a chart you can see, and each number leads back to the passages behind it.

- **Query**: find passages by a rule (a code, codes that occur together, a case or variable, a date range, words in the passage) and list the excerpts.
- **Code Matrix**: codes across the columns, and documents, cases, the values of a variable, or months down the side, counting codings, excerpts, documents, or cases, as numbers or percentages.
- **Code Relations**: how often codes occur together or one comes before another.
- **Code Summary**: a profile of each code.
- **Crosstabs**: cases by two variables.
- **Visualizations**: bar charts of the counts.
- **Concept Map**: draw how your codes relate, with labelled links, and keep the map.
- **Saved queries** can be named, **frozen** (so you can see later what they found at that moment), and compared with what they find now.
- **Document Portrait** shows where the coded passages fall along each document. For every document that has coded words it draws one strip from the first word to the last, with a mark for each passage at its place (passages that overlap are stacked, so none hides another); the line under the title says what share of the document is coded. Press a mark to open its passage in the document. Choose *The codeline of one document* to give each code in that document a row of its own, which shows at a glance which codes run all through it and which come only at the start or the end. Open *The numbers for ...* under a picture for the same facts as a table: for each code the passages, the characters coded, the share of the document, and where its first passage starts and its last ends. The *Codes drawn* list leaves codes out of the drawing. Only words are drawn (an area of a picture or a stretch of a recording has no place along a text), the working set narrows it, and a very coded document draws its first 600 passages and says so.

## Text Analytics

The **Text Analytics** tab opens a page with two tools. Both read the words of your documents; a picture's description is never counted.

- **Word frequencies** counts the words your documents use, the commonest first. A word is a run of letters or digits, written in lower case; nothing is stemmed or guessed. Choose the documents (every document, or the documents of one case) and, if you like, only the words inside passages given one code (a code includes its sub-codes). *Leave out common English words* is on to begin with; turn it off for another language. You can leave out short words and choose how many words to list. Each word shows how often it is used, its share of the words counted, and in how many documents; **See where** looks it up in context.
- **Keywords in context** finds a word or the words of a phrase and shows the words round each place it is used, in reading order. **Open** takes you to the document at that word.

## Statistics

The **Statistics** tab opens a page for the variables of your cases. It has three parts: the **variables** on the left, the **output notebook** in the middle, and the **chooser** on the right.

**This page describes, and the tests are done in PrismStatistics.** To begin with, the chooser offers one thing, *Describe one variable*: counts and shares for categories, and the mean, spread, quartiles, and shape of numbers, with the charts that go with them. The tests of difference, association, and prediction (t tests, analysis of variance, chi-square, correlations, regression, and the rest, described below) are PrismStatistics's work, and the card at the top of the page says so. Its button **Make the case table for PrismStatistics** saves the cases of the project as a file PrismStatistics opens with a double click (see *Reports and exports*): one row for each case, with the variables you see on this page and a variable for every code. If you want the tests here as well, press **Show the tests here too** on that card, or choose *Describing and testing* in Settings > Analysis; the page then offers everything described in the rest of this section, and **Only describe here** puts it back. The choice belongs to this computer, and nothing already in a project's notebook is lost either way.

**Every row is a case, and never a coding.** A case is a person, a site, or a family, with the variables it carries (the columns of the spreadsheet you imported, for example). Many codings come from one person, and a test that counted each coding as a separate person would count that person many times and report a finding that is not there. So what a case said about a theme enters the tests as **one value for each case**: *Has the code* (yes or no, whether any of the case's documents carry the code or one of its sub-codes) and *Excerpts coded* (how many distinct stretches of text or areas of a picture carry it, so two coders on the same words count once). A case that holds no document has no code values.

**Missing values are set aside, and the page says how many.** A blank, a value the project marks as missing, and a word in a variable that is meant to hold numbers are all left out of a test that needs that variable, and each page says how many cases were used and how many were set aside.

**Only some of the cases.** Under the options is *Cases to use*. Write a rule, such as `age >= 30 & group == "B"`, and *Check the rule* says how many cases it picks. The test is run on those cases only, and the notebook page says which rule it used. A rule that picks no case is refused, and so is one that gives numbers and not true or false. Rules are written in the same language as the formulas of the data editor (see below).

**The chooser asks what you want to do, and offers only the tests that are valid.** Choose a goal (describe one variable; compare groups on a number; compare two numbers on the same cases; compare a number with a value; see whether two categories go together; relate two numbers), choose the variables, and the tests that fit appear: for two groups, Welch's t test (which does not assume equal spread; tick the box for Student's) and the Mann-Whitney test; for three or more, the analysis of variance and the Kruskal-Wallis test, each followed by every pair of groups (after the analysis of variance you choose Tukey's honestly significant difference, Games-Howell, Scheffé's test, or t tests adjusted by Holm, Bonferroni, or Benjamini-Hochberg; after Kruskal-Wallis, Dunn's test adjusted the same way; Holm unless you choose another); for two categories, the chi-square test, and Fisher's exact test when the table is two by two; for two numbers, Pearson's, Spearman's, and Kendall's correlations. A rank-based test (Mann-Whitney, Kruskal-Wallis, Wilcoxon, Spearman, Kendall) can use an ordinal variable whose values are numbers; a test of means needs a scale variable. A nominal variable is never offered where a number is needed. When a grouping variable has more than two values, tick the groups to compare.

**More tests.** Beside the first set, the chooser offers these where they are valid. *Describe one variable* adds the **Shapiro-Wilk** test and the **Kolmogorov-Smirnov** test against a normal curve for a number (give the mean and standard deviation of a curve you have a reason for; if you leave them out the sample's own are used and the page says the p-value is then too large), the **runs test** of whether the order of the cases looks random (for a number it cuts at the median, the mean, or a value you give; the order is the order of the cases in the project), and for categories the **binomial test** (the share of cases in one category against a share you name, with an exact interval) and the **one-sample chi-square** test (whether the counts follow equal shares or shares you give). *Compare a number with a value* adds the **sign test**, and so does comparing two numbers on the same cases. *Compare groups on a number* adds, for two groups, the **Kolmogorov-Smirnov** test of whether the whole distributions differ, **Mood's median test**, and the **Moses test** of whether one group is more spread out than a control group, and for three or more groups the median test. *See whether two categories go together* adds **McNemar's test** when the two variables have the same two values (the same people answering twice), and the measures of order, **gamma, Kendall's tau-b, Stuart's tau-c, and Somers' d**, when both are ordered and made of numbers. Two goals are new: *Compare three or more measures on the same cases* (Friedman's test, with Kendall's W for how much the cases agree; choose the measures with *Add a measure*) and *Relate two numbers, holding others constant* (a partial correlation; choose what to hold constant with *Add a variable to hold constant*).

**Two groupings and scales.** *Compare groups on a number, by two groupings* runs a **two-way analysis of variance** of a number by two variables: each variable's effect with the other taken into account, and what the two do together (the interaction), with type III sums of squares, the partial eta squared of each effect, the count, mean, and standard deviation of every combination, and the means of each value of each variable. Every combination of the two variables needs at least one case. The page does not compare single pairs of combinations: read them from the table of means. *Check how well several items measure one thing* runs **Cronbach's alpha** of two or more numbers measured on the same cases (the items of a scale): alpha, the standardized alpha, the mean correlation between the items, an interval for alpha (Feldt's), each item's correlation with the sum of the others, and what alpha would be without it; it says when pairs of items correlate negatively (an item scored the other way round) and which item, left out, would raise alpha. Only the cases that have a value for every item are used. Both are checked against R and have their R code in the recorded script.

**Each run adds a page to the notebook**, with:

- the tables, laid out as APA 7 tables (no vertical lines; p-values and correlations without a zero in front);
- a **results sentence** such as a report would write it, with the statistic, degrees of freedom, p-value, effect size, and interval;
- a **plain reading** that says how large the effect is by the usual benchmarks and what the numbers do not show. A result that is not statistically significant is reported as not statistically significant, with the size of the effect and its interval, and is never called *marginal* or *trending*;
- **What the test depends on**, a list of checks with a word for each state (*Fine*, *Note*, *Problem*, or *Design*): how many cases there are, whether the numbers are close to symmetric or have outliers, whether the groups have similar spread (Levene's test), whether the counts in a table are large enough, and how many values are tied. A check that fails does not stop the test; it says what to use instead;
- the cases behind each group, which you can list.

**Curve fits.** Choose *Fit a curve to two numbers*, the number to explain and the number that explains it, and tick the curves to fit (all eight by default; at least one stays ticked): **linear**, **logarithmic** (a straight line in the logarithm of the predictor), **inverse** (in one over the predictor), **quadratic** and **cubic** (one and up to two bends), **power** (the outcome is a constant times the predictor to a power), **exponential** (the outcome changes by a constant share for each unit of the predictor), and **S curve** (the logarithm of the outcome in one over the predictor). Each is fitted by least squares, after the logarithm or the reciprocal where the curve needs one. The page gives one table that compares the curves (what each was fitted on, R squared, adjusted R squared, F, p, the equation with its numbers, and **the R squared and the root mean squared error on the scale the outcome was measured on**), a table of coefficients for each curve, one chart that draws the points and every curve (each in its own color and line style, with a legend), and a table beside the chart that gives each curve's value at every case. **Compare curves by the R squared on the scale of the outcome**: the power, exponential, and S curves are fitted to the logarithm of the outcome, so their first R squared is on that scale and cannot be compared with the others. A more flexible curve (quadratic, cubic) fits the cases at least as well as a simpler one, and may bend to follow chance: look at the picture and the adjusted R squared, and prefer the simpler curve unless the extra bend is clear. A curve that cannot be fitted to these numbers (a logarithm of a number that is not above zero, a reciprocal of zero) is named in the results with the reason, beside the curves that were. Compound and growth curves, which statistical packages list, are the exponential curve written another way and are not offered twice, and the logistic curve with an upper bound is not built.

**Logistic regression.** Choose *Explain a yes-or-no from other variables*, the outcome (a variable with exactly two values among the cases used; whether a case has a code is one), and one or more predictors, chosen as for a regression (numbers, or categories against a reference; steps if you want to see what each step adds). The page models the odds of one of the two values against the other: **the later of the two** by default, or `1` when the outcome has it (so a code's *yes*), or the one you choose under *Model the odds of*. Choosing the other value turns every odds ratio over. The page gives the fit (the deviance, the likelihood-ratio chi-square against a model with only an intercept, and for models in steps the change between them), three pseudo R-squared measures (McFadden, Cox and Snell, Nagelkerke, which are not shares of variance), AIC and BIC, the **area under the ROC curve**, a table of observed against predicted outcomes (a predicted probability of .5 or more counts as the value modelled) with the share classified correctly for each, the Hosmer-Lemeshow test of fit and its groups, the coefficients (B, its standard error, z, p, the **odds ratio** with a Wald interval and, for the model reported, a profile-likelihood interval, which is the better of the two with few cases), a likelihood-ratio test of each variable left out (a categorical variable with all its columns at once), and the cases that pull the fit most. The checks it makes: how many cases of the rarer outcome there are for each predictor term (ten or more is the usual guide), whether the predictors are strongly related to each other, whether one case has too much influence, whether any standardized residual is extreme, and the Hosmer-Lemeshow test. A bootstrap adds intervals for each coefficient and for the area under the curve. When the predictors separate the two outcomes perfectly or all but perfectly (for example every case in one category has the same outcome), the coefficients have no best value, and the page says so instead of giving numbers. An odds ratio of 2 doubles the odds of the value modelled; it doubles the probability only when that value is rare.

**Regression.** Choose *Explain a number from other variables*, the number to explain, and one or more predictors with *Add a predictor*. A predictor can be a number, or a categorical variable, which becomes a 0/1 column for each category except one, the **reference** that the others are compared with (the first category unless you choose another). Whether a case has a code is one such predictor (yes against no). An ordinal variable made of numbers is used as a number, and the page says so. Tick *Enter the predictors in steps* to give each predictor a step: the page then fits one model for each step, with every predictor of that step and the steps before it, and shows what each step adds to the share of variance explained (R squared change, with its F test). The page gives the model summary, a table of coefficients for each step (B, its standard error and interval, the standardized coefficient, t, p, and the variance inflation factor), a sentence for the model and for each predictor, and a list of the cases that pull the fit most, by Cook's distance. The checks it makes: how many cases there are for each predictor term, whether the predictors are strongly related to each other, whether one case has too much influence, whether the residuals are close to symmetric, whether the spread of the errors is even (the Breusch-Pagan test), and whether any residual is extreme. A regression needs more cases than parameters, and a predictor that is the same for every case used, or that can be worked out exactly from the others, is refused with the predictor named.

**The bootstrap.** Where it means something (the description of a number, the t tests, Mann-Whitney, Wilcoxon, the correlations, and regression), tick *Add bootstrap intervals*. The cases are drawn again and again, with replacement, and the statistic is worked out on each draw; the spread of those values gives an interval that rests on fewer assumptions than the usual one. You get a percentile interval, and where one set of cases is resampled a BCa interval (corrected for bias and skew) as well; for the difference between two groups, which are resampled each within itself, the percentile interval only. Choose the number of resamples (2,000 is a good start) and see the **seed**: the same seed gives the same intervals, so a result can be repeated, and *A new seed* gives other draws. It is offered up to 5,000 cases (500 for Kendall's tau).

**Charts.** Each page of the notebook has the charts that go with its test, drawn under the results sentence. A description of a number has a **histogram** and a **normal probability plot** (the closer the points lie to the line, the closer the values are to a normal distribution); a description of a category has a **bar chart** of counts. A comparison of groups has a **box plot** of each group (the box holds the middle half of the cases, with a bar at the median; a diamond marks the mean; the whiskers reach the furthest values within 1.5 box lengths, and a circle is a value beyond them) and, for the tests of means, the **mean of each group with the interval of that mean**. A table of two categories has **stacked bars**: one bar for each row, split into the share of its cases in each column, with a legend and the share written in each segment. A correlation has a **scatter plot**, with a straight line for Pearson's r. A regression has the **residuals against the fitted values** (a model that fits shows no curve and no funnel; the line marks zero), the **normal probability plot of the residuals**, and, when one number predicts, the data with the **line the model fitted**. A test of one number or of pairs has a histogram with a dashed line at the value compared with, or at zero for the differences.

Every chart has a title and a **text alternative** that says what it shows, in words, for anyone who cannot see it. Hover a mark, or tab to it where a chart has few marks, and its numbers are written under the chart. *Show the numbers behind this chart* opens the table of exactly what is drawn, which is the way to read a value off a chart, and to see every case of a scatter. Colors never carry meaning alone: groups are named on the axis, and where colors stand for categories (stacked bars) a legend names them, each segment is outlined, and the share is written in the segment on a label of the page's own color, so it can be read whatever the color behind it. The words in a chart grow and shrink with the text size in Settings, as the rest of the window does. A chart is drawn in the colors of the theme in use (light, dark, or high contrast) and in the system colors when Windows high contrast is on; the words have at least 4.5 to 1 against the page, and the marks and the axis at least 3 to 1. In a window too narrow for a chart, the chart scrolls sideways inside its own box (which the keyboard can reach) and the page itself does not. A scatter shows at most 3,000 points (every few cases when there are more, and it says how many are left out); the numbers and the tests always use every case.

**The bootstrap of the whole analysis, and of whole groups of cases.** Under *Bootstrap* you also choose **what to bootstrap**. *The main statistic of this test* is the bootstrap above, offered where a test has one. *The whole analysis* runs the test itself again on each resample of the cases and gives an interval for **each of the numbers it reports** (the test statistic, the p-value, the effect size, each coefficient of a model, the R squared, the area under the curve, and so on: the numbers the page leads with, in a table called *Bootstrap of the whole analysis*), and it is offered for every test, including the ones with no single statistic of their own (the analysis of variance, Kruskal-Wallis, chi-square, Fisher, and the tests of counts and ranks, regression, logistic regression, and curve fits). The intervals are percentile intervals only (there is no bias-corrected one), and for a p-value the table also says in **what share of the resamples p fell below .05**, which tells how stable the conclusion is. Under *Resample* you can draw **whole groups of cases** instead of single cases: the cases that share a value of a variable (comments in one thread, people in one family, answers from one site) are drawn together, which keeps cases that resemble each other together and gives wider, more honest intervals when cases in a group are not independent. A variable is offered when it has at least five groups among the cases, and a group is drawn with replacement, so some are left out of a resample and some appear twice; a case with no value of the variable is a group of its own. Resampling groups runs the whole analysis. A whole-analysis bootstrap is offered up to 5,000 cases (500 for Kendall's tau), at most 5 million runs of the analysis in all (cases times resamples), and is stopped after three minutes; a resample on which the analysis cannot be run (a group left out of it) is counted and not used, and if more than half cannot be, the page says so and gives nothing.

**The recorded script.** Every page of the notebook has the **R code** that makes its numbers (open *The R code for this page* under the page, and *Copy the code*). *Export the notebook*, choosing **R script**, saves all the pages as one script, `name.R`, and the data it reads as `name-data.csv` beside it: a row for each case, a column for each variable of cases, and a column for each code the pages used (whether a case has it, or how many excerpts carry it). Open the script in R with the folder of the two files as the working directory and run it: each page is a section, in the order the pages were run, headed by its title, and prints the numbers the page shows. The analyses are written with R's own functions (`t.test`, `aov`, `chisq.test`, `cor.test`, `wilcox.test`, `lm`, `binom.test`, `friedman.test`, ...); where R has no function (Games-Howell, Dunn's pairs, the runs test, the Moses test, Somers' d, partial correlation, the exact interval of Cohen's d), the script defines a helper at its top, the same one the engine is checked against. A test on some of the cases starts with the rule you gave (`subset(data, rule)`). A variable you made in the data editor is in the data file with the values it had when the script was saved. **The bootstrap** is in the script too. PrismQDA draws its resamples with a fixed random-number generator (SplitMix64) and the script writes the same generator out in R, so from the same seed R draws the same resamples and prints the same intervals: for the statistic of a page (a mean, a difference, a correlation, the coefficients of a regression) and for the whole analysis, whether the cases or whole groups of cases were resampled. R does this in its own language, which is slower than PrismQDA, so a script with several bootstraps of thousands of resamples can take minutes to run. **The charts** are drawn too: if any page has a chart, the script opens a PDF named after the data file (`name-charts.pdf`, beside the other two files) and draws every chart of the notebook into it, one to a page, in the order of the pages, with the numbers behind each chart printed as *Show the numbers behind this chart* shows them (the points of a scatter plot or of curves are drawn but not printed). The script is yours to change; the page does not change when you do.

**Taking results out of the notebook.** *Export the notebook* (above the pages) saves every page as one file: **Word** (a heading for each page, its results sentence and reading, **numbered APA 7 tables** with rules above and below the header and below the last row, no vertical lines, and the note under the table, and each chart as a **numbered figure** with its text alternative; Word's navigation pane lists the pages), **Excel** (a Contents sheet and a sheet for each page; a table value that is a plain number is a number in its cell, and a value such as `< .001` or `1,200` stays text exactly as the page shows it; charts are pictures), or a **web page** (one file for any browser, with a contents list, the tables with their headers marked, and the charts as drawings that have a text alternative; to make a PDF, print it from the browser). Every sentence and label in the file is the page's own, in the language of the window. *Save as picture* under a chart saves it as a **PNG** (twice as many pixels across as the chart has on the page) or an **SVG** (a drawing that stays sharp at any size). A saved chart is always drawn in the light colors on a white background, whatever theme the window is in, so it reads in a document. *Copy table* puts a table on the clipboard as tab-separated text, which a spreadsheet pastes into cells, and as an HTML table, which Word pastes as a table. A file that is already there is never replaced unless you chose its name in Windows' own save window.

**The notebook is kept in the project.** Each page you run is saved in the project file with the request that made it and the result it gave, so closing the project and opening it again brings the notebook back as it was. (The project file is format 10; a project from an earlier version is brought forward when it is opened, as before, and an untouched copy is kept.) Each analysis page carries **your note** (a text box under its tables, saved when you leave it, and included under the page in an export), a **section** (a name you give; when any page has one, a row of tabs shows one section at a time, or all pages, or the pages in none), and buttons to **move** it up and down. *Add a page of notes* adds a page of your own writing, with a title and a body, which sits among the analyses and is not numbered with them. Above the pages an **index** lists every page, and choosing a line takes you to it. *Remove* takes a page out of the notebook for good, with the earlier runs kept for it.

**Running the analyses again after the data change.** *Run all the analyses again* (above the pages), or *Run this analysis again* on one page, runs each analysis on the project **as it is now**: a variable you edited, a case you added, a code you changed. A page whose new result differs from its old one **keeps what it said before** as an earlier run (the last twenty are kept), shows a table of the numbers the page leads with, the earlier run beside this one with the change, and says how many cases were used each time. A page that comes out the same says that nothing changed. An analysis that cannot be run any more (a variable it names was deleted) stays as it was, with the reason. A page that was run again in an earlier session offers *Compare with the earlier run* when the project is opened. The analyses are run again from what was asked, so a rule that picks cases or a list of cases is read again too; a bootstrap uses its saved seed, so it gives the same intervals unless the data changed.

**What the numbers are checked against.** Every procedure here is compared with R on invented data, and the validation report (`docs/VALIDATION-REPORT.md`) lists each with its tolerance and says where PrismQDA differs from R and why. Two things are worth knowing. The p-value of Spearman's correlation is exact for up to 9 pairs, comes from the series approximation R uses (it calls it exact) for 10 to 1,290 pairs, and is the t approximation when there are ties, and the page says which. And the intervals of Cohen's d and Hedges' g are exact (they come from the noncentral t distribution), where they were once approximate.

**Which test for the pairs of groups?** Tukey's test is the usual choice when the groups have a similar spread; the page's checks say whether they do (Levene's test). Games-Howell does not assume equal spread or equal sizes, so choose it when the checks say the spread differs. Scheffé's test is the most cautious: its p-values and intervals hold for every comparison of groups, not only pairs, so they are the widest. The adjusted t tests are the simple option when only a few pairs matter. **Shapiro-Wilk.** Each check of the shape of a variable now shows the Shapiro-Wilk test beside the skewness and kurtosis. It does not change the verdict (*Fine*, *Note*, or *Problem*): with few cases it has little power to notice a departure from a normal shape, and with many it notices departures too small to matter, so it is to be read with the shape and the plot.

**Counting cases by a weight, and running an analysis for each group.** Under *Cases to use* on the test chooser, *Count each case as many times as* a variable of numbers says (a whole number, 0 or more; a case with 0 or with none is left out) gives what the test would give if each case were written out that many times, and the page says so and how many cases that came to. Only whole-number weights of this kind (frequency weights) are built, and a bootstrap cannot be added to a weighted analysis. *Run it for each group of* a variable runs the same test on each group by itself and puts each group's page in a section named for the group (for example *Site: North*); each page keeps the rule that picks its cases, can be run again, and has its own R code.

## The Data editor

The **Data editor** (Statistics tab, then *Data editor*) is where the variables of your cases are made and changed. It has two views.

**The data view** is a grid with a row for each case and a column for each variable. Move with the arrow keys; **Enter** or **F2** (or just typing) changes the cell, **Enter** saves it and moves down, **Tab** saves it and moves right, **Escape** puts the old value back, and **Delete** clears it. Every saved cell is one step in the history, so **Undo the last change** takes it back. A variable that takes numbers refuses a word and says why; a date variable takes a date written year-month-day. Where a variable has value labels the grid shows the words and keeps the value, and a screen reader hears both. A value the variable counts as missing is shown in italics with a dotted underline, and is announced as counted as missing. A long list of cases is shown a hundred at a time; the row numbers are those of the whole table.

**The variable view** lists each variable with its level of measurement, its value labels, the values that count as missing, and how it was made. *Change* edits the name, the level, the labels (one to a line, as `1 = Agree`), and up to three values that mean missing. *Delete* removes a variable with its values, and Undo brings it back.

**Making a variable from others.** The toolbar has five ways, and each shows what it would make (how many cases get a value, the level, and the first cases) before anything is saved.

- **Compute** takes a formula in R's own syntax: arithmetic (`+ - * / ^ %% %/%`), comparing (`== != < <= > >=`), joining (`& | !`), `%in%`, `ifelse(test, yes, no)`, `round(x, digits)`, `pmin`, `pmax`, `abs`, `sqrt`, `exp`, `log`, `is.na`, and across the variables of one case `rowmean`, `rowsum`, `rowmin`, `rowmax`, and `nmiss`. A name with a space goes in backticks, and the buttons under the box put the names in for you. A missing value in a formula makes the answer missing, as in R.
- **Recode** gives chosen values new ones (`1, 2` become `Low`; `99` becomes missing), and a value no rule names stays or becomes missing, as you choose.
- **Standardize** makes z-scores: how many standard deviations each case is from the mean.
- **Rank** gives each case its place, ties sharing the average place, lowest first or highest first.
- **Cut into ranges** turns a number into ranges at cut points you write. Each case gets the number of its range, and the range, such as `(30, 50]`, is the label.

A made variable keeps how it was made. It is **not** kept up to date behind your back: if the variables it came from change, *Make it again* (in the variable view) brings it up to date. Giving a new variable the name of one that exists asks you to tick that it replaces it, and Undo puts the old one back.

**Three more ways to make a variable** are in the same window.

- **Part of a date** takes the year, quarter, month, week, day, day of the year, weekday, or hour out of a variable whose level is *date* (values written year-month-day, like 2024-03-14, with a time after it if you want the hour). Months and days of the week carry their names. The week is the ISO week, so the days around New Year can belong to the last week of one year or the first of the next, as in R's `%V`. A value written another way (14 March 2024) has no parts, because the program does not guess whether 3/4/2024 is March or April.
- **Random sample** chooses some of the cases at random and makes a variable that says 1 for a case in the sample and 0 for one that is not. Say how many cases, or what percent. *Draw within the groups of* a variable takes the percent from each group (so a small group is not left out by chance); a case with no value in that variable cannot be drawn. The **seed** is a whole number: the same seed over the same cases always gives the same sample, so write it in your methods and the sample can be drawn again; *Make it again* draws the same sample unless the cases changed.
- **Group summary** works out what each group of cases comes to (the mean, sum, median, smallest, largest, standard deviation, how many of the group have a value, or how many cases it has) and writes it on every case of the group. The groups are the cases that share a value of the variable you tick, or of all the variables you tick. A case with no value in one of them is in no group and gets none.

**Sort cases** puts the cases in order by up to three variables (low to high or high to low; the case's own name is a choice too). It only changes the order the data view shows, says so above the grid, and writes nothing to the project; *Show them in their own order* undoes it. A case with no value comes last.

**Merge from a file** brings columns of a spreadsheet (.xlsx), a text file of values (.csv, .tsv), or an SPSS file (.sav) in as variables of your cases. Choose the file and press *Read the file*, say which column is the key and what it is matched with (the name of the case, or the values of a variable; capitals and spaces at the ends do not matter), tick the columns to bring, and say what each is called and its level (the level is a guess from the values; a column of numbers is refused if it holds a word, and a column of dates if it holds a date written another way). A case the file has no row for gets no value. A row that matches no case brings nothing in, and the result names a few of them. When two rows have the same key the first is used, and the result says how many were not. If a variable of that name exists you can tick that it is filled in for the cases the file has; the others keep what they had. Each variable is its own step in the history.

**Tables and restructuring** makes three kinds of table. A row of Statistics is always a case, so these are shown here and **saved as a CSV file or an Excel workbook** for another program, and are not kept in the project.

- *A table with a row for each group of cases*: tick the variables that make the groups and add summaries (for example the mean and the count of a score); the table says how many cases are in each group, and how many were left out because they have no value in a variable that makes the groups.
- *Wide to long* stands columns on end: the columns that are the same thing measured more than once (three waves of a score) become a row each, beside the columns kept on every row (who the row is about). Choose the names of the two new columns, and whether a row with no value is left out. It can start from the cases or from a file.
- *Long to wide* lays observations across: rows that share a who become one row, with a column for each observation. It can start from the cases or from a file. Two rows for the same who and observation cannot be laid across; the window names the first pair so you can correct the file.

Not built here: weights that are not whole numbers, a lag or a difference over time, and adding cases from a file.

## Mixed Methods

The **Mixed Methods** tab opens a page for moving between the two kinds of data. Nothing it makes is hidden: a variable it makes is in the Data editor, and a code it makes is in the Codebook.

**Codes into variables** makes a variable of cases from the coding. Choose how it should read:

- *Whether a case has a code* gives Yes or No: some excerpt of one of the case's documents carries the code.
- *How many excerpts carry a code* gives a number for each case. The same words coded by two coders count once.
- *Which of several codes a case has most* gives a category: the code carried by the most excerpts. Codes that tie are named together (`Trust and Doubt`), and a case that has none of them is `None`.

*Show what it would give* shows how many cases get a value and the first cases, and saves nothing. A case that holds no document has no value, since there is nothing to code. A code also stands for its sub-codes unless you untick that. The new variable is an ordinary variable of cases: Statistics and a rule can use it, and the Data editor says how it was made. It does not follow the coding behind your back; *Make it again* in the Data editor's variable view brings it up to date when the coding has changed.

**Variables into codes** turns the values of a variable of cases into codes. Choose the variable (a variable of free text is not offered), name the parent code if you want a name other than the variable's, and tick the values you want. The page says how many codes it would make and how many cases and codings each would get, before anything is made. *Make the codes and code the text* makes a code for each value under the parent and codes each case's text with the code of its value, as you. A query or the code matrix can then speak of "the cases in this group" in the language of the coding. Right after it is made, *Take back what was just made* removes exactly the codings it made and retires the codes it made (they stay in the Codebook, retired, and every removal is in the history); a coding of those codes that you made by hand is left alone. Later, retiring a code in the Codebook does not remove its codings. In a project that codes whole units, each unit of a case's documents is coded.

**Joint displays** is the second tab of the Mixed Methods page. A joint display puts what people said beside what is known about them, on one page. They are worked out from the project each time you look, so they never go stale, and nothing in them is kept in the file.

- The *crosstab* and the *segment matrix* are in Explore (Crosstabs, and the Code Matrix by a variable); the tab has buttons that lead there.
- The **case-ordered display** puts the cases in the order of a variable (a number from lowest to highest, or words in the order of the alphabet, either way round) and shows, for each code you choose, how many excerpts of the case carry it and the first few of them quoted. *Open* beside a quotation opens the document at those words, and *Show all* opens every excerpt behind the count. You can show other variables beside the one it is ordered by, and show every case, even those with no coding of the codes. A case with no value of the ordering variable comes last whichever way the order goes.
- The **typology table** describes groups of cases formed by codes, a group being the cases that have the code. Choose the codes and the variables to describe the groups with. For a number the table gives how many cases have a value (*n*), the mean, and the standard deviation; for categories it gives *n* and the count and share in each category. The first row is all the cases, the last is the cases that hold text and have none of the codes, and a case that has two of the codes is in both groups. *Show the cases* lists the cases of a group. Variables of free text, and variables of categories with more than twelve different values, are not offered.

- The **side-by-side display** has a row for each topic (a code you choose). In one column is what people said about it (how many excerpts, the first few quoted, with *Open* and *Show all*); in the other are the variables you choose for the cases that have the topic and for the other cases that hold text, with the difference of the means for a number.
- The **deviation table** takes the groups made by the values of one variable and, for each group, lists the codes its cases have more often than all the other cases (*most typical*) and less often (*least typical*). Each row shows how many cases of the group and of the others have the code, the difference in points, and *z*, the adjusted standardized residual: how far the group is from what the other cases would lead you to expect. With many codes and groups some will pass 2 by chance, so read it as a guide to where to look and not as a test. *Show the cases* lists the cases behind a row.
- **Similarity analysis** says which cases are most alike on the codes and variables you choose, with a number from 0 to 1 for each pair (Gower's similarity, which suits a mixture of codes, numbers, and categories). Two cases that both lack a code are not compared on it unless you tick the box for that. *Show how* gives a pair feature by feature, and *Show the table of every pair* gives them all for up to 60 cases.
- The **code by variable bubble plot** has a bubble for each combination of the values of two variables: its size is how many excerpts of the code the cases in it have, and its colour is the mean weight of those codings (when the code is rated). Beneath it is the same table of numbers, one code across two crossed variables, and *Show the excerpts* opens the words behind a cell. *Save as picture* saves the chart as PNG or SVG.
- **Design and integration** is the third tab, and keeps what you decide. *Design and templates* lets you choose one of four designs (convergent, explanatory sequential, exploratory sequential, or embedded), say which strand has priority and why you are mixing the two, and set up what the design needs: the page shows beforehand the few variables and theme codes it would make (and leaves any that are already there as they are), and writes the first line of the log. It does not move documents. *Triangulation matrix* has a row for each topic with what the words say and what the numbers say in your own words, an optional code and variable that the words and numbers behind the topic are shown from, and your mark: convergence, complementarity, or discordance, and why. *Integration log* is a dated record of where and how you brought the two together, and why; on the Codes and variables tab, *Record this in the integration log* adds a step you have just made. The report can carry the design, the log, and the matrix as its *Mixed methods* section.

## Auto Code

Auto Code finds passages by a rule you can read and suggests a code for each. Nothing is coded until you accept it in the **review queue**, where you can correct it. No AI is used. The rules: the turns of chosen speakers, the sections under headings, or the words you search for (with a number of words around each match). A decision in the queue can be taken back with one Undo.

## The AI Assistant

PrismQDA never connects to an AI service. The AI Assistant builds a **packet** of text (your codebook and some passages, with what to answer and in what form). You take it to any chatbot you choose and paste the answer back. The answer is **checked before anything of it reaches the review queue**: a passage or code that was not in the packet is refused, and every quoted word must appear in its passage, word for word. What passes waits in the review queue as an *AI suggestion* until you accept it.

- A packet carries **words only**. Pictures are left out and counted. A document or a code marked **do not share** is never in a packet.
- Every run keeps what was sent, what came back, and what became of it, in the **AI use log**, with a paragraph for your methods section.
- AI can be switched off for a project (Settings), and then no packet can be built.

## Working with other coders: the Team page

The **Team** tab opens a page for working with other coders. At the top you choose the **coders** to compare: every person who codes is chosen to begin with; an AI model only if you tick it. The page has three tabs.

### Agreement

How well do the chosen coders agree? Choose:

- **One code for each unit** (each coder gave each unit one code) or **each code on its own** (did the coder apply this code to this unit?).
- **Which units**: every unit that at least two of the chosen coders coded, or a random sample by number and seed (the same number and seed draw the same sample again).
- **What to call it**: the usual word, intercoder reliability, or concordance. A run with an AI model in it is called concordance, because a model is not an independent coder.
- Whether to include the **areas coders drew on pictures**. Pictures are compared on a 16 by 16 grid laid over each picture; neighbouring cells are not independent, so treat the figures for pictures as a guide.

The result is a sentence that says whether Krippendorff's alpha meets the target, a table of coefficients with intervals, a table of the codes least agreed first, for two coders a table of how their codes line up, notes, and a **written report** to copy. Every run is kept in the project. A run that is **not archived keeps its documents from being edited**, so the figures always describe the text they were worked out on; archive a run to free them. Runs can be opened again later.

### Disagreements

Every unit two or more of the chosen coders coded differently, in reading order, with its words and what each coder gave it. For each you decide which codes the unit should carry (none at all says that no code applies) and **write why**. A decision can be changed, and taken back with Undo. Tick **Hide who coded what** to settle blind: the coders become Coder A, Coder B, and so on, in an order that changes from unit to unit. **Open in the document** jumps to the unit. Decisions are kept apart from every coder's own coding, which is never changed, and they appear in the report.

Below the units, **Areas and stretches** lists the areas of pictures and PDF pages and the stretches of recordings that some of a document's coders marked and others did not (areas of one code that overlap by at least half count as the same area). Each shows a small picture of the area, or its times, and who marked it and who did not. **Accept into the final layer** or **Leave it out**, and write why; a decision can be changed, and taken back with Undo.

**The final layer.** What the project says once the disagreements are settled: for each unit, the codes of its decision where it was decided, the codes the coders gave it where they agreed (or only one coded it), and nothing where the coders still disagree and no one has decided. It is worked out each time from the codings and the decisions, so it is always what they say now. Choose it in **View > Filters > Working Set** (*Use the final layer*; the dialog says how many units are decided, agreed, and still open) and Retrieved Segments and Explore (the summary, the matrix, the relations, queries) count it instead of every coder's own codings, or tick **Use the final layer** when you export the coded passages. A decision's coding is the decider's, with the reason as its reason. Areas of pictures and pages and stretches of recordings are in it too: an area every coder of the document marked is final, and one that only some marked is left out until you accept it into the layer or leave it out in the Areas and stretches section of Disagreements (it asks for your reason, as a decision on words does); the Working Set dialog says how many are decided, agreed, and still open. Words coded without a unit are not in it.

### Packets

To give another coder some of the work, make them a **packet** on the Team page (the *Packets* tab). Say who it is for, choose all the documents or only some, write instructions (they will see them as a memo), and press *Make the packet*: a small project file is saved beside yours, or where you say. It holds the codebook, the documents you chose, and the instructions, and **nothing else of the study**: not your other documents, your memos, your notes on the analysis, or the history. It holds none of the codings made so far, so the coder works blind; tick *Also include the codings made so far* if you want them to review them instead. The packet is **not encrypted**, so send it the way you would send the documents themselves. Recordings do not travel in it (a recording is linked by where it is on your computer); the coder links their own copy.

The coder opens the packet in PrismQDA. It says at the top whom it was made for, and the person using it is that coder, whatever their own name. They code, close the project, and send the file back. You bring it in with **Merge** (below): their coder is added, or, if you named someone who is already in your project, their codings go to that coder, and nothing of yours is changed. While the list of names to replace is applied to what you export, a packet is refused, because it holds the documents whole.

### A class exercise

To teach with a coding exercise, use the **Class** tab on the Team page. It is a short way to do what the Packets and Merge tabs do for one coder, for a whole class, and then to see how the class did.

1. **Code the exercise yourself first.** Your coding is the answer key the class is compared with.
2. **Make a packet for every student.** Paste the names from your roster, one on each line (a name that comes twice is used once), choose the documents or leave them all, and write the instructions. One small project file is made for each student, in the *class folder* (a folder beside your project is suggested, and it is made when it is not there). The packets hold the codebook and the documents and none of your coding, so the students work blind. Send each student their own file. A file that is already there is never replaced, and the page says so for each one.
3. **Put the files they send back in the class folder and bring them in.** *Bring in the students’ work* takes in every packet of this project in the folder, after one backup: each student becomes a coder and keeps their own coding. A file that is not a packet, or that cannot be read, or that holds documents this project does not have (it may belong to another study), is listed and left where it is. Bringing the same files in again changes nothing. A student who sent the packet back with nothing coded is a student too. If a document was changed after you made the packets, the codings on it cannot be placed: the list says so for that student (*partly*), and the review would count every student as having left that document uncoded until the packets are made again. If a student added a code of their own to the codebook, the list says which, and the code is in your codebook now.
4. **Review the class.** Choose the instructor (you, to begin with), the students (every other person who codes, to begin with), and the documents (all, to begin with), and press *Review the class*. For each student the table says how many passages they coded and, of the passages you coded, how many they coded with exactly your codes, with some of them, with other codes only, or left uncoded; and the share of your passages that are the same and of your codes that they found. A table of the codes shows which the class found hardest (the average share of your passages with that code that the students gave it too, how often students gave it where you did not, and their average kappa with you). Under the tables are the passages the class coded least like you, each with its words, your codes, the codes students gave that you did not, and the codes they left out, so the exercise can be talked through in class.

Tick *Call the students “Student 1”, “Student 2” and so on* to show the review to the class: no name or number that leads to a name is in it, and the order does not follow the names. *Save the table* writes a CSV file with a row for each student, to open in a spreadsheet; it is not changed by the list of names applied to other exports, because the names are what it is about.

**The heat map and the passages side by side.** Under the table of codes, the heat map has a row for each student and a column for each code you used, the hardest for the class first. A cell is the share of your passages with that code in which the student gave the code too, so a dark column is a code the class found hard and a row of dark cells is a student to look at again. The percent is written in every cell; the shading only helps the eye. *Show the passages side by side* lays your codes beside every student's for the passages listed above (the hardest ones), one row for each passage, with *same* under a student who gave exactly your codes. When the review calls the students by number, so do the heat map and this view, and Student 3 is the same student in all three, so the class can talk about the coding and not about a person. Both can be saved as CSV files for a slide or a spreadsheet; a file that is already there is not replaced.

**Feedback for each student.** Under the review, *Make a feedback file for each student* writes a Word file for every student in a folder of its own (by default *Feedback* in the class folder; it is made when it is not there, and a file that is already there is not replaced). A student's file says how their coding compares with yours (the same codes, some of them, other codes only, left uncoded, coded where you did not, and the codes they found, missed, and added), and then lists the passages where their codes were not yours, with the words of each and the two sets of codes, in four groups: the passages they left uncoded, those they coded with other codes, those where some of their codes match, and those you did not code. A passage they coded exactly as you did is counted and not listed. A file holds that student's name and nobody else's, and no figure of the class; the files are made by name even when the review above is set to call the students by number, because a student reads their own. The first sentence of each file says what a passage is, and what the review left out (pictures, PDF areas, and recordings are not compared) is said at the end.

A passage here is a unit of the text as it was imported (a paragraph, a turn, or a sentence), and a student has given it a code when a coding of theirs with that code lies in it; a passage they did not code counts as left uncoded, which is an answer in an exercise. Pictures, PDF areas and recordings are not compared, and the review says how many it left out. What is not built yet: coach mode for students, a file for the whole assignment with the settings locked, an answer key kept apart from the project, a heat map of codes against students, feedback for each student as a Word file, and a side-by-side view of several students’ coding.

### Merge

Coders who worked apart on copies of the same project can bring their work back. Type the path of a copy (or Browse) and **Check what would be merged**: the page says which documents, coders, codes, codings, areas, links, memos, cases, and variables would come in, and what it would leave out and why, and changes nothing. **Merge it now** saves a backup of your project first. The copy is only read.

- Documents the copy has and you lack are added. For documents you both have, the codings, areas, and memos are combined, each kept with its coder.
- People are matched by their coder id, codes by their place in the codebook, documents by name and words, cases by name, and variables of cases by name.
- Cases the copy has and you lack are added with the documents they hold; variables you lack are added with their values. A value you already have is kept, and a different one in the copy is listed with its case and variable; so is a code whose wording differs. Each has a box, *Use the copy's*, and there are buttons to take the copy's for all of them or keep yours for all: whatever you tick takes the copy's when you merge, and everything else keeps yours. A variable of the same name at another level is left out and named.
- A code worded differently in the copy keeps your wording and is listed. A document with the same name and other words is left out and named.
- A merge is too large to undo one step at a time; Undo stops there, so the backup is the way back.

## Reports and exports

The **Report** page has these cards, and the Export dialog has the same choices.

- **Report.** *Build a report* makes one Word document from the project's own records, in the sections you choose: the study, the documents, the codebook, the coded passages (areas of pictures cropped), agreement between coders, adjudicated decisions, memos, the paragraph about the use of AI, a **draft methods appendix**, and a timeline of notes and milestones. Every figure is a count and every sentence a record; a section with nothing to say says so. The methods appendix is a draft: it cannot know why you made your choices, so read it and add your reasons.
- **Codebook.** Export as Excel, Word, CSV, or the QDC exchange format that other qualitative programs can read. To bring a codebook in, press **Import Codebook** on the Code ribbon (or the menu of the Codes pane, or Ctrl+K and type *codebook*) and choose a `.qdc` file: its codes are added with their tree, themes, colours, and definitions, and a code that is already at that place in the codebook, by name, is left as it is, so reading the same file twice adds nothing. A file is read whole or not at all: one that is too big or too deep is refused before any code is added.
- **Coded passages.** Export every passage, or one code, or one coder, as Excel (with a second sheet counting by code and coder), Word (grouped by code, with where each came from and who coded it), or CSV. In Word and Excel an area of a picture is the picture **cropped** to the area, with a description for a screen reader; CSV keeps the area in words.
- **The case table for PrismStatistics.** *Export > The case table for PrismStatistics* (or the button on the Statistics page) saves a `.pstat` file, the project file of PrismStatistics. It has **one row for each case**, never one for each coding, with the case's number and name (tick *Leave out the names of the cases* to keep only the number), a variable for each variable of your cases (a number stays a number, with its value labels and missing codes; a date is written year-month-day, and a date written another way is left empty and listed; an identifier such as 007 stays text), and for each active code two variables: whether any document of the case carries the code, and on how many distinct excerpts (an excerpt coded with a sub-code also counts for the code above it unless you turn that off). A case that holds no document has no value for a code. Retired and merged codes are left out, and the file says how many. No passage, memo, or coder is written, and the list of names to replace, if you applied it to exports, is applied to the names and texts in the file. The window says what the file holds and lists everything it left out or changed. A code's or case's number is never given again in a project (since project format 16), so a table made later can be matched to an earlier one; a project upgraded from an earlier format starts from the highest number it holds.
- **The whole project.** *Export > The whole project* saves the project in the REFI-QDA project format (`.qdpx`), which other qualitative analysis programs can open: the codes, the coders, the documents and their codings, pictures with their coded areas, PDFs with their text, cases and their variables, memos, links between passages, concept maps (as graphs), recordings with the stretches coded on them, and sets of codes; the coded rectangles of PDFs are written in points from the bottom-left of the page, as the standard names them, documents with their kind and their units, and transcripts with the times of their lines. The window then lists what the format cannot hold, for example ratings and the statistics notebook. A recording is written as an audio or video source that says where the file is on your computer; tick *Put the recordings inside the file* in the export dialog to put the files themselves in (a recording over 512 MB, or past 1 GB in all, is left out and named), otherwise whoever opens it elsewhere needs the recording too. The documents go into the file whole, with any names in them, and the file is not encrypted even when the project is; while the list of names to replace is applied to exports, this export is refused. To bring a project in from another program, choose **Import QDPX** on the Welcome page (or press Ctrl+K and type *QDPX*): it is read into a **new project** beside the file, the project that is open is not changed, and a report lists what came in and what did not. A document that PrismQDA wrote comes back with the kind and the units it had; any other arrives as a document split into sentences. A graph becomes a concept map (a box that stands for a code, a case, or a memo that came in is that thing, and any other box is a free note with its words). A value the file puts on a document goes to the case that holds the document, or to a case made for it. An audio or video source becomes a document, from its transcript or with a line about it, and the recording is linked when the file is found on your computer or is inside the archive; the stretches coded on it are coded again, and without the recording they are left out and counted. The sync points of a transcript become the units of its document, each with its time, so the player follows the text, and the selections made between sync points become codings of the words between them. A coded rectangle on a PDF page comes in where it was drawn, by its page, its points, and the page's turn and crop box; one whose page is not in the PDF is left out and counted. A file made by QualCoder 4.0 is read the way QualCoder counts (a text it saved on Windows has its line breaks counted as one character, and its PDF rectangles are measured from the top left of the page), and the report says so when that mattered; QualCoder does not bring in links between passages, concept maps, or the documents a case holds, so they do not arrive in its copy.
- **A project from ELAN.** In ELAN, *File > Export Multiple Files As > REFI Project File...* writes a `.qdpx`; *Import QDPX* here reads it. Each recording becomes one document made of its transcript, with the recording linked (if the file is still where ELAN found it: ELAN's *include the media* choice wrote no recording into the file when it was tried without ELAN's window), the times of its lines, the codes of a coding tier under a transcript tier as codings of that speaker's words, and the codes of a coding tier on the recording as coded stretches. ELAN gives the codings of words no coder, so they arrive as *Imported (QDPX)*; the speaker labels and times ELAN writes into each line stay in the words.

A file you ask to save is never allowed to replace one that is already there unless you choose the file in Windows' own Save dialog.

## Pseudonymize and redact

Open it from the **Import** tab, under **Prepare** (the button **Pseudonymize and redact**), or with the command box.

A **pseudonym** is a made-up name or label, such as Participant 3. A **redaction** puts a mark, such as [phone], where the words were. Either way the words are really taken out: nothing is hidden under a black box that could be lifted. You write a **list**: the words to find, and what takes their place. Then you choose how to use it.

**The list.** Under *Add to the list*, write the words to find, one on each line (the full name on one line, the first name on the next), and the one label that takes their place. *Capital letters matter* keeps Will from finding will. *Whole words only* (the default) keeps Ann from being found inside Anne. A comma, a double quote, a tab, or a line break cannot be in a label, because it could break the columns of a spreadsheet. Lines with the same label are shown as one line, and *Change* and *Remove* work on the whole line. The list finds **exactly** what you write: it does not understand sentences, so it misses a nickname, a spelling mistake, or a detail such as the only dentist in town. Read the result before you share anything.

**Suggestions.** *Look for names and identifiers* looks through the documents for speaker labels (not interviewers), case names (not codes such as P07), email and web addresses, phone numbers, numbers written like an identity number, and words that begin with a capital letter in the middle of a sentence. A full name and a first name found alone get the same label. These are guesses made by rules, not by a model: take out what is not a name, and add what it missed. Tick the ones to add; *Add the ticked words as one person* gives them all the label of the first ticked row.

**What the list would do.** *Show what the list would do* counts what the list finds in each document, shows a few examples before and after, lists the documents that cannot be changed (PDFs, pictures, and documents in an agreement run that has not been archived), and lists the other places that hold the words (document names, memos, cases, and so on). Nothing is changed by looking.

**For what you export.** Tick *Replace these names in everything I export*. While it is on, every Word, Excel, and CSV file, the report, and every packet you take to a chatbot has the list applied on its way out, and the export window and the AI page say so. The project is not changed, so nothing is lost and you can change the list at any time. What the chatbot sends back is checked against the words it was shown and placed on the real words. Not covered: pictures and PDF pages (their areas are told in words and the picture is left out), a chart saved as a picture (you are told), text you copy with a Copy button (except the packet for a chatbot), and a copy of the whole project file.

**Change the project for good.** This replaces the words in the text of your documents and in the places that copy text: the names of documents, speaker labels, notes on codings, cases and their values, the codebook, memos, concept maps, saved queries, the statistics notebook, the mixed methods tables, the AI log, and **the audit trail** (an audit trail that still holds the names would defeat the purpose; it ends with a plain entry saying what was done). Codings stay on the same words: a coding on a name is a coding on its label afterwards.

- A **backup** is made first, and nothing is changed if it cannot be made. The backup keeps the names, and so do the earlier backups of this project in the same folder (the page counts them): keep them somewhere private, or delete them when you no longer need them.
- The list holds the real names, so it is **taken out of the project** afterwards. Type a place for a **key file** in the *Key file* box before you press the button (or save it first with *Save the list as a key file*): a CSV of each word and what replaced it. The page warns you while that box is empty. Keep it apart from the project; it is plain text and not encrypted, so keep it somewhere private. *Add the words in a key file* reads it back, for a document you add later that has the same names. Without a key file, only the backup can tell you who is who.
- PDFs and pictures cannot be changed, so they are left as they are and listed. The sound of a recording and the file names of linked recordings are not changed either.
- The file is then rewritten so the old text is not left in unused parts of it. The page lists any place where the words are still found, so you can deal with it before you share the project.
- **Undo cannot take this back.** Only the backup can.

**Make a copy to share.** To share a project without the names and keep your own, use *Make a copy with the names replaced* on this page. It writes a new project file (choose where; the file must not exist yet) with the names replaced for good **in the copy only**, in the documents and in every place that copies text, as above. This project, its list, and its backups are not touched, and nothing is made beside the copy: no backup, and the copy does not hold the list (save the key first, from the Key file box, if you will need to know who is who). Pictures and PDFs cannot be changed, so the copy leaves them out, with the areas coded on them (their text stays, with the names replaced); links to recordings are left out too (the recordings are not copied); agreement runs in progress are archived in the copy so their documents can be changed; and an encrypted project's copy is encrypted with the same passphrase. The page then lists what was replaced, what was left out, and any place where the words are still found, which you should deal with before you share the copy. The copy's name ends with *(names replaced)*. Keep the project, with the names, where only you can reach it.

### The offline lock and the ethics summary

At the bottom of the Privacy page. **Lock this project offline** is a switch kept in the project: PrismQDA connects to nothing on its own, and the lock is the project saying so and holding to it. While it is on, no prompt packet can be built for an AI service from this project, Check for updates is refused, the bottom of the window says *Offline lock on*, and the ethics summary says so. **Make the ethics summary** opens the report with one section chosen, *Ethics and data handling*, and saves a Word file that states what an ethics board or a protocol amendment asks for: where the project file and its backups are kept, whether it is encrypted, the lock, every prompt packet that was built (when, how many passages, the model you named, and how the answer was judged), the documents and codes marked do not share, whether a list of names to replace exists and is applied (the names themselves are never repeated), who coded (a person or an AI model), and how long the record of what was done is. It is made from the project and nothing else, and it says that what you did outside the program is not recorded. *Ethics and data handling* is also one of the sections you can choose when you build any report.

## Encrypted projects

An encrypted project's file cannot be read without its passphrase: every page of it is encrypted, and so is the write-ahead file beside it. **A lost passphrase cannot be recovered by anyone.** Nothing about it is kept, there is no recovery key, and nobody can help: not you, not a friend, not the author of this program.

- **Turn it on.** *Settings > Privacy & Security > Protecting a project > Encrypt this project…* Type a passphrase twice (at least eight characters; four unrelated words is a good one, and *Show the passphrase* lets you check what you typed). A warning window then says in plain words that nobody can open the project if the passphrase is lost. PrismQDA writes a new, encrypted file, checks it, puts it where the old file was, and overwrites the old file with zeros before it deletes it. You can also tick *Encrypt this project with a passphrase* when you make a new project.
- **Open it.** An encrypted project asks for its passphrase when you open it, from the recent list or *Open Project*. A wrong passphrase is told and asked again. The recent list says *Encrypted*, and so does the status bar while the project is open.
- **Backups.** A backup of an encrypted project is encrypted with the same passphrase (so is the one made when the project opens, and the copy kept when a project is brought to a newer format). Backups made **before** are not: after you turn encryption on, the plain ones still hold everything, and after you change the passphrase, the older ones still open with the old one. The panel counts them and offers *Overwrite and delete them*; *Look for backups this passphrase does not protect* does the same whenever you ask.
- **Change it, or turn it off.** *Change the passphrase…* asks for the current one and the new one twice (and shows the warning). *Turn encryption off…* asks for the current one and leaves an ordinary project file.
- **Merging.** On the Team page, a copy that is encrypted asks for its passphrase. If you leave it out, this project's own passphrase is tried, because a team often shares one.
- **Other programs.** The file is SQLCipher 4 compatible (AES-256-CBC, an HMAC-SHA512 on each page, a key made by PBKDF2-HMAC-SHA512 at 256,000 rounds), so a program that opens SQLCipher 4 files, such as DB Browser for SQLite or the `sqlcipher` tool, opens it with the passphrase (put in Unicode NFC first, which changes nothing for a plain English one). The command-line tool reads the passphrase from the `PRISMQDA_PASSPHRASE` environment variable, never from the command line.

What it does **not** protect: the project while it is open (its text is in your computer's memory like any open document); the files you choose to make from it (Word, Excel, CSV, the report, and the key file of Pseudonymize and redact are ordinary files; use that page to take names out of them); the recent list, which keeps the project's name and where its file is; and any older bytes a solid-state drive, a cloud folder, or a file history may keep of a file that was not encrypted before. Pictures, PDFs, and notes inside the project are protected with it; a recording is a file elsewhere, which is not.

## Settings, language, and backups

Open **Settings** from the gear in the title bar. Settings belong to you and your computer, not to a study, so every project opens the same way. Its sections:

- **General**: the language of the window, and **your name in the project history**: every change you make is recorded in the project under this name, and you appear under it as a coder. Left empty, PrismQDA uses a name it made for your computer ("Researcher" and four characters); it is never your Windows sign-in name. People who each work on their own copy of a project and merge the copies later should each use a different name. The language of the window is English. A translation is a file someone made elsewhere (a spreadsheet saved as CSV, or JSON). *Add a translation* reads it, checks it, and shows what it found before keeping it; *Save a file for a translator* gives the English in one column and an empty column to fill in. Each translation carries a label, who made it, and whether a person or a machine did. The translator's guide is `docs/TRANSLATOR-GUIDE.md`. PrismQDA does not translate for you.
- **Interface**: the theme (light, dark, or high contrast), the colour used for highlights, and the text size. The whole window scales with the text size.
- **Project Defaults**: where new projects are saved, and how many dated backups to keep for each project. Backups stay beside each project, or in a folder you choose. Every change is saved as you make it; there is no timer and nothing to remember to save.
- **Coding**: whether the small coding bar appears above words you select with the mouse, and the rules of the open project (whether it codes any words or whole units, its mutually exclusive groups, and its rated codes).
- **Analysis**: where the analysis pages begin, on this computer. For the Statistics page: the **confidence level** of intervals (90, 95, or 99 percent; 95 is the usual), **how pairs of groups are compared** (Tukey, Games-Howell, or Scheffé after an analysis of variance, or an adjustment of the p-values: Holm, Bonferroni, Benjamini-Hochberg, or none), the number of **bootstrap resamples** (1,000 to 10,000; 2,000 to begin with), and whether every bootstrap **begins with the same seed** (and which) so that a result can be repeated, or with a new one each time. For queries, code matrices, and code relations: whether **a code also stands for its sub-codes** to begin with. Each analysis page still lets you change these for the analysis in front of you; a change here is felt on the Statistics page and in Explore at once.
- **AI Assistant**: whether prompt packets may be built in this project, and what is never put in one.
- **Team & Sharing**: who has coded in this project, and where to compare coders and merge copies.
- **Privacy & Security**, **Accessibility**, **Updates**, and **About**.
- **Updates**: the version of this program and one button, **Check for updates**. PrismQDA never looks for a new version by itself: nothing is checked when it starts, in the background, or on a schedule. When you press the button it asks one address (on github.com) whether a newer version has been published, and sends what every web request sends, the version of this program and the kind of computer, and nothing from any project. If there is a newer one it shows the notes, and installing is a second step: **Download and install** asks you to confirm, downloads the installer, checks its signature against the key built into this program, saves and closes the open project, and runs it for the current user; your projects are left alone. Nothing is installed if the signature does not match. It does not check while the open project has the offline lock on, and a portable copy is not updated in place (it tells you to download the new zip from the releases page). A version that was built before the update key was set up shows that it cannot check, and says where new versions are published.

## The keyboard and screen readers

PrismQDA is built to be used with the keyboard alone and with a screen reader.

- **F1** opens the list of every shortcut. **F6** and **Shift+F6** move between the main areas. **Escape** closes a window or a menu.
- In the text, single keys (1 to 9, I, R, U, N, E, Enter) work only while the text has the focus, so they never interfere with typing in a box.
- Every table has a header row and a caption; every picture has a description; every chart has a table beside it; colour is never the only way something is said. What you do is announced ("Coded 'felt welcome' as Welcome").
- The window follows your computer's theme, and Windows high-contrast mode is respected.

## Privacy: what stays on your computer

- The program connects to nothing on its own. The one exception is **Check for updates** in Settings (see *Updates* in the Settings section above). The installer carries Microsoft's WebView2 setup for a computer that lacks it (Windows 11 has it), so it downloads nothing.
- Your project file holds all your data. Exports and reports are files you choose to make and choose where to put.
- Documents and codes can be marked **do not share**, which keeps them out of AI packets.
- A list of names can be applied to everything you export, or to the project itself (see [Pseudonymize and redact](#pseudonymize-and-redact)).
- A photograph's camera facts (and especially its place) are kept only if you tick them.
- The project's **log** records what was done, by whom, and when. It is part of the file, and the methods appendix and timeline are built from it.
- A project can be **encrypted** with a passphrase (see [Encrypted projects](#encrypted-projects)); one that is not encrypted is an ordinary file, so protect it with your computer's own tools (a locked account, an encrypted drive) if the material is sensitive.

## What is not built yet

- Mixed Methods is built as the book describes it (moving between codes and variables, six joint displays, the design templates, the triangulation matrix, and the integration log). Statistics has descriptions, t tests, one-way analysis of variance, chi-square and Fisher's tests, correlations, and the rank-based tests; its notebook, kept in the project, has no way yet to export a page of notes. Text Analytics has word counts and keywords in context only; stems, topics, and sentiment are not built.
- For recordings: stepping through video frame by frame, a waveform that can be zoomed, saving a clip in the recording's own format (clips are WAV files), and a chart of codes over time for one recording. On a PDF page an area is a rectangle; coding the words where they sit on the page layout is not built.
- For pseudonymizing: a check for details that together identify a person, and rules written as patterns. For encrypted projects: a recovery key, a hardware key, remembering the passphrase, and encrypting single documents.
- In Team: a tie-breaker role with a sign-in.
